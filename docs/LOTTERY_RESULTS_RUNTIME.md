# Lottery results runtime

The independent Results card never writes Lottery Accounts, receipts, PWD, balances or financial sync state.

## Delivery and storage

The frontend reads a small public `documents.json` manifest from GitHub and caches link metadata for a rolling thirty-day window on the device. PDFs open directly on the government/provider hosts. They are not stored on Render, in Supabase or in the repository. A saved link is not an offline PDF. The compact view does not download the legacy winning-number feed. Refresh occurs on opening, online, foreground and every 120 seconds while visible. Selecting another draw never substitutes a previous draw's document.

The QR decoder is lazy-loaded and runs on the device. No photo is uploaded. Camera access starts only after Scan QR; stops after a reading, explicit stop, backgrounding, thirty seconds or unmount. Only plain full Dear ticket text is currently recognized (`35B 00220` or `35B00220`). Unknown QR formats and URLs are not guessed or opened; use manual entry. Actual printed-ticket QR formats still require device acceptance with representative tickets. Date/time must be confirmed explicitly; scanning does not submit a check or payment.

## Ticket verification service

`orbis-lottery-ticket` is a separate, authenticated, read-only Edge Function. It uses the existing central session verifier, fixed provider ticket-check endpoint, byte/time limits, strict same-ticket acknowledgement and a server-only token. Only a single-ticket verdict is returned; no provider dataset is exported. Pending, invalid, not-found and unavailable are never translated to no prize. Client edits, draw changes and unmount cancel stale checks.

Each isolate bounds cached verdicts to 256, reuses published verdicts for sixty seconds, pending statuses for five seconds, coalesces identical concurrent calls and admits provider calls at most once per 1.1 seconds. Verified identities have a three-second admission interval. These are per-isolate protections, not a global quota guarantee. Provider 429 responses produce a retry-later state. High-volume rollout requires measured traffic and a provider plan/global admission policy; do not promise unlimited ticket scans.

Activation requires `SAMBAD_API_TOKEN` in **Supabase Edge Function Secrets**, in addition to the GitHub secret of the same name. Never add it to Vite, browser storage or source. The existing `VITE_KHATA_DATA_URL` selects the sibling ticket-function URL. Configure allowed web/native origins and the existing central identity URL. Deploy this new function with platform JWT verification disabled because the handler itself verifies ORBIS central bearer sessions; do not bypass the handler's verifier. No SQL migration or existing financial Edge redeployment is needed. A matching frontend deployment and Android rebuild are separate actions; native camera permission is optional and requested only when scanning.

## Result collection

The API workflow has one serialized worker at IST 13:10, 18:10 and 20:10. It retries pending publication every thirty seconds, stops at the corresponding :30 deadline, succeeds once per draw and has a hard 41-attempt bound. GitHub can start late or miss a scheduled run; this is best-effort scheduling, not real-time delivery. Manual dispatch supports a selected date and individual slots or `6pm,8pm`. A blank manual date selects yesterday in IST (20 November for the initial 21 November test). A legitimately unpublished draw is reported as unavailable without replacing any saved PDF; credential/identity failures still fail the job. Retention is rolling thirty days; full historical backfill is not implied.

Only a successful published same-date/slot API response and validated PDF allow publication of its public link. Government sources are selected by operator:1PM/8PM use Nagaland’s selected-date index;6PM uses the Sikkim Dear6PM archive form. The Sambad API still identifies all three as lottery=dear with the selected slot; lottery=sikkim is its separate4PM Labhlaxmi family. The UI state label follows the draw. Sikkim’s form streams a PDF after an observed POST; the collector validates exact selected-date DN filename, PDF MIME/signature and byte cap, and publishes only an allowlisted officialSource descriptor. A user gesture submits only the selected date to that fixed government form, not ticket/customer data. Older manifest readers safely ignore the optional descriptor. Filename prefixes are not a reliable draw identity: `DG` can identify Dear Laxmi, not Dear 6 PM. Missing official publications remain unavailable; absence from the Nagaland index does not imply a Sikkim6PM result is unavailable. PDF retrieval is not an independent comparison of every winning number. The old OCR collector remains manual-only for review; it does not run alongside the automatic API schedule.

GitHub CI includes the new Edge entry in strict Deno checks and Knip's entry graph. Full coverage, mobile/desktop Chromium and Android candidate remain runner checks. Real camera/printed QR, live ticket verdict and scheduled upload timing need separate acceptance; unit mocks do not prove those outcomes.
